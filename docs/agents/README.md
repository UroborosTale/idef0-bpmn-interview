# Агенты: Cline и субагенты

Модель процесса строят и правят агенты Cline (главный агент и субагенты), но **агент только предлагает — применяет человек**.
Приложение не вызывает LLM для этой работы: модель, ключи и расходы — на стороне Cline в VS Code.

```
Cline (главный агент + субагенты) ──MCP──▶ MCP-сервер process-modeling ──HTTP──▶ приложение
                                                                                   │
аналитик в студии ◀── вкладка «Предложения агентов»: применить / отклонить ◀────────┘
```

## Подключение

1. В `.env` приложения задайте токен агента и запустите приложение:
   ```
   AGENT_API_TOKEN=длинная-случайная-строка
   ```
   Токен открывает агенту только ручки `/api/agent/*`: прочитать модель и проверки, отправить предложение. Применить или
   отклонить предложение, править модель напрямую и остальное API агент не может. Без `AUTH_USERS` (локальная разработка)
   вход отключён, токен не нужен.
2. Соберите сервер: `npm run build -w server` (MCP-сервер запускается из `server/dist/mcp/index.js`).
3. В Cline откройте MCP Servers → Configure и добавьте сервер по образцу
   [cline_mcp_settings.example.json](cline_mcp_settings.example.json): путь к `index.js`, `PM_API_URL` (адрес приложения)
   и `PM_AGENT_TOKEN` (тот же токен). Для разработки без сборки: `npm run mcp -w server` (tsx).
4. Откройте этот репозиторий в VS Code: правила из `.clinerules/` подскажут Cline, как работать с моделью.

Названия пунктов меню и параметров конфигурации Cline (`autoApprove` и др.) могут отличаться в вашей версии — сверьтесь с
документацией Cline.

## Инструменты MCP-сервера

| Инструмент | Что делает |
|---|---|
| `get_conventions` | Правила Соглашения и формат предложений — читать до первого предложения |
| `list_sessions` | Сессии: id, процесс, код |
| `get_model` | Конспект модели: коды `B002.01.01`, id для ссылок, должности, шаги BPMN, замечания проверок; `scope` — ветка по коду; `view=full` — JSON |
| `get_fragments` | Текст интервью по фрагментам с id — для цитат в `source` новых записей (приложение проверяет, что цитата есть во фрагменте) |
| `propose_patch` | Отправить предложение: список операций (`task_id` — по какому заданию). В ответе — описание правок и влияние на проверки (снимает/вносит замечания) либо ошибки |
| `list_proposals`, `get_proposal` | Статус предложений. У отклонённых — **причина отказа**: агент учитывает её в следующих предложениях |
| `get_tasks`, `take_task`, `complete_task` | Задания аналитика из студии (вкладка «Задания агенту»): взять, выполнить предложениями, завершить с итогом |
| `add_questions`, `list_questions` | Вопросы к интервью (интервьюер): сохранить пакет до 20 вопросов — с адресатом, функцией (код `B002.01.02`), «зачем» и приоритетом — и посмотреть уже заданные и отвеченные. Дословные повторы приложение отбрасывает; не больше 10 ожидающих вопросов на функцию и 60 на сессию. Вкладка «Вопросы» |
| `add_report`, `list_reports`, `get_report` | Отчёты (аналитик; нормоконтролёр и методолог — для развёрнутых итогов): заголовок, краткое содержание, выводы структурой (что, где, основание, влияние, уверенность, рекомендация) и полный текст. Список без полного текста, целиком — `get_report`. Вкладка «Отчёты»; не больше 30 непрочитанных на сессию |
| `create_task` | Поручение другому агенту (нормоконтролёр → моделист): обратная связь внутри команды; аналитик видит и может отменить; не больше 20 незавершённых на сессию |

## Формат предложения

`propose_patch` принимает `session_id`, `agent` (роль: методолог, моделист, нормоконтролёр, интервьюер, аналитик), `title`,
`rationale` (почему: цитаты интервью, правило, замечание проверки) и `ops`:

```json
[
  { "op": "add", "collection": "nodes", "value": { "id": "n1", "type": "task", "name": "Открыть реестр", "bpmn_scope": "o1", "role_id": "r2" } },
  { "op": "update", "collection": "nodes", "id": "n1", "patch": { "name": "Открыть реестр процессов" } },
  { "op": "remove", "collection": "flows", "id": "f3" },
  { "op": "set_assignments", "node_id": "o1", "items": [{ "role_id": "r2", "kind": "executor", "functions": ["Внесение данных"] }] },
  { "op": "set_process", "patch": { "code": "B002.00.00" } }
]
```

Коллекции: `roles`, `systems`, `data`, `controls`, `nodes`, `flows`, `pools`, `messages`. Предложение проверяется до сохранения:
ссылки (исполнитель, входы, выходы, системы, родитель, диаграмма) должны существовать, id не повторяются, поток не соединяет
шаги разных диаграмм, запись соответствует схеме модели. При любой ошибке не сохраняется ничего — агент получает список ошибок.
Новые шаги приложение помечает гипотезами, пока аналитик их не подтвердит. Описание формата — `server/src/shared/patch.ts`.

## Что делает аналитик

Вкладка **«Предложения агентов»** внизу студии (и кнопка «Предложения (N)» в ленте):
- видно, что изменится — по-русски, с кодами по Соглашению, — и как изменятся проверки;
- **«Применить»** кладёт правки в черновик студии одним шагом истории: их можно отменить (Ctrl+Z) и сохранить как обычно;
- **«Отклонить…»** записывает причину — агент увидит её через `list_proposals`;
- метка «модель изменилась» — модель сохраняли после предложения; если правки уже нельзя применить к черновику
  (шаг удалён, ссылка пропала), «Применить» недоступно, причина показана.

## Подготовка и проверка связи

| Команда | Что делает |
|---|---|
| `npm run agent:check -w server` | Проверяет готовность: приложение отвечает, токен принят, MCP-сервер запускается отдельным процессом и отдаёт 16 инструментов; при сбое — что исправить |
| `npm run agent:demo -w server -- <id сессии>` | Имитатор агента: отправляет демонстрационные предложения (удачные и «неудачное»), берёт и закрывает задание. Репетиция вкладок «Предложения агентов» и «Задания агенту» до подключения Cline. Предложения называются «Демо: …» — их можно отклонять |
| `npm run seed:b002 -w server`, `npm run seed:c025 -w server` | Загружает эталон B002 или процесс C025 (по документу «ДПО от 05.10») новой сессией (общая команда: `seed:process -- <имя>`; при включённом входе — `PM_LOGIN`, `PM_PASSWORD`) |
| `npm run eval:b002 -w server -- <id сессии \| файл.json>` | Сравнивает модель с эталоном и печатает отчёт (см. ниже) |
| `npm run agent:prompt -w server -- <роль>` | Системный промпт роли для модели без Cline: общие правила + инструкция роли + Соглашение |

## Задания аналитика агенту

На вкладке **«Задания агенту»** аналитик формулирует поручение («разбей операцию B002.01.02 на шаги по интервью»,
«проверь роли»), при желании привязывает его к выделенной функции и адресует роли агента. Агент забирает задание через
`get_tasks`/`take_task`, отвечает предложениями с `task_id` и закрывает задание `complete_task` с итогом. Задание ждёт агента,
пока тот не обратится к MCP-серверу, — постоянное соединение не нужно. Видно статус, итог агента и предложения по заданию.

## Роли агентов и обратная связь

У каждой роли своя инструкция. Общие правила (`.clinerules/00-process-modeling.md`) Cline подгружает всегда, инструкция роли — это workflow в `.clinerules/workflows/`, он вызывается через `/` в чате. Одинаковая структура у всех: роль, **границы** (что делает и чего не делает), подготовка, порядок, завершение.

| Workflow | Роль | Что делает | Меняет модель? |
|---|---|---|---|
| `methodologist` | методолог (главный агент) | Забирает задания и распределяет их ролям, ведёт цикл «моделист ↔ нормоконтролёр» (не больше двух кругов на функцию), отвечает на вопросы по Соглашению, предлагает структуру процесса (код, подпроцессы, владельцы) | предложениями, только структура |
| `model-from-interview` | моделист | Читает всё интервью и предлагает модель по порядку: справочники → структура IDEF0 → BPMN каждой операции → роли; у всего — цитата-источник | предложениями |
| `review-model` | нормоконтролёр | Проверяет модель по Соглашению и сверяет с интервью; механическое исправляет предложениями, остальное поручает моделисту (`create_task`) или возвращает вопросом аналитику | предложениями, механическое |
| `interviewer` | интервьюер | Собирает пробелы (`model.gaps`, замечания проверок, гипотезы), отбрасывает то, на что интервью уже ответило, и готовит вопросы: открытые, ненаводящие, ≤ 5 на тему и около 15 на интервью, с адресатом и привязкой к коду | нет: итог — список вопросов |
| `analyst` | аналитик | Выводы по готовой модели: время и ожидания, передачи между исполнителями, согласования, повторный ввод, циклы, нагрузка; каждый вывод с кодом, основанием, влиянием и уверенностью; перечень данных, которых не хватает | только измеримые факты из интервью (сроки, частота) |
| `work-tasks` | методолог | Забирает задания аналитика и передаёт их ролям | — |
| `propose-fixes` | нормоконтролёр | Короткая проверка связки: замечания проверок → предложения исправлений | предложениями |

Интервьюер и аналитик сохраняют результат в приложении: вопросы — `add_questions` (вкладка «Вопросы»), отчёты — `add_report` (вкладка «Отчёты»); краткий итог остаётся в `complete_task`. Оба хранилища только для чтения человеком и агентами: модель они не меняют, а правки по ним агент предлагает отдельно (`propose_patch`).

**Вопросы.** Аналитик видит список по важности (критично → желательно) с адресатом и «зачем», отмечает вопрос заданным, получившим ответ (можно записать текст ответа) или снятым; кнопка «Копировать для интервью» собирает лист по функциям в порядке процесса — без отвеченных и снятых. Ответ в модель вносит моделист по новым фрагментам. Снятый вопрос можно задать заново — повтором он не считается.

**Отчёты.** Новый отчёт отмечен в счётчике вкладки; щелчок по заголовку раскрывает таблицу выводов и полный текст и отмечает отчёт прочитанным; «В архив» убирает его из списка (вернуть можно флажком «с архивом»).

Данные хранятся в таблицах `agent_questions` и `agent_reports` (удаляются вместе с сессией). Ручки для студии: `GET /api/sessions/:id/agent-questions`, `POST /api/agent-questions/:id/status`, `GET /api/sessions/:id/agent-reports`, `POST /api/agent-reports/:id/status`; для агентов — `/api/agent/sessions/:id/questions|reports` и `/api/agent/reports/:id`. Тест `server/test/roles.test.ts` следит, чтобы инструкции ссылались только на существующие инструменты MCP и поля модели.

### Модель без Cline

Для модели, которая работает не через Cline (собственный сервер, API напрямую), системный промпт роли собирается из тех же файлов — общие правила, инструкция роли и правила работы с моделью, правила хранятся в одном месте:

```
npm run agent:prompt -w server -- нормоконтролёр
npm run agent:prompt -w server -- аналитик --out analyst-prompt.md
```

Ответы моделей лучше сравнивать на одном и том же эталоне (`eval:b002`) — так видно, какая роль или версия инструкции ошибается.

Обратная связь моделиста и нормоконтролёра идёт заданиями (`create_task`) и отказами аналитика (причина в `list_proposals`).
Будет ли роль запускаться как субагент Cline или главный агент выполнит её по очереди — зависит от возможностей установленной
версии Cline; приложению это безразлично, все пользуются одним MCP-сервером и подписываются в `agent`.

## Измерение качества: эталон B002

`server/src/reference/b002.ts` — эталонная модель процесса B002 «Управление процессами ООО «РУ КМЗ»» по IDEF0 (уровни 0–1) и
BPMN девяти операций из документов организации: 3 подпроцесса, 9 операций, 175 элементов, 159 стрелок, 3 должности, 34 продукта.
Эталон проходит все проверки Соглашения без замечаний (его коды совпадают с документами: `B002.01.00` … `B002.03.04`).
Отступления от исходных диаграмм описаны в заголовке файла: код B002 вместо C037, события-факты вместо существительных у
B002.01.01, объединённые одноимённые продукты.

`eval:b002` сопоставляет названия по корням слов (окончания и порядок слов не важны) и считает полноту, точность и F1 по
функциям, шагам BPMN, последовательности шагов, должностям, продуктам и системам, а также нарушения правил Соглашения у
кандидата. Одним и тем же эталоном можно сравнивать разные модели LLM, роли и версии инструкций. Рекомендуемый порядок
замера: загрузить текст интервью по B002 в пустую сессию, выполнить `model-from-interview`, применить предложения,
выполнить `eval:b002`.

## Порядок внедрения

1. **Каркас и формат правок** — готово.
2. **Моделист и нормоконтролёр с обратной связью** — заготовки ролей, задания, фрагменты, проверка цитат, эталон — готовы; настройка по реальным запускам после подключения Cline.
3. Методолог (главный агент) — инструкция и распределение заданий готовы; панель «Ассистент» и доработка по запускам — после подключения Cline.
4. Интервьюер — инструкция готова (вопросы в итоге задания); отдельное хранилище вопросов — позже.
5. Аналитик — инструкция готова (выводы в итоге задания); сводка и передача выводов интервьюеру через задания.

Инструкции всех пяти ролей — первая редакция. Правьте их по реальным запускам: что агент делает не так, дописывайте в «Границы» или «Правила качества» той роли, а не в общие правила.
