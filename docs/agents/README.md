# Агенты: Cline и субагенты

Модель процесса строят и правят агенты Cline (главный агент и субагенты), но **агент только предлагает — применяет человек**.
Приложение не вызывает LLM для этой работы: модель, ключи и расходы — на стороне Cline в VS Code.

```
Cline (главный агент + субагенты) ──MCP──▶ MCP-сервер process-modeling ──HTTP──▶ приложение
                                                                                   │
аналитик в студии ◀── вкладка «Предложения агентов»: применить / отклонить ◀────────┘
```

## Подключение

1. В `.env` приложения задайте токен агента и запустите приложение:
   ```
   AGENT_API_TOKEN=длинная-случайная-строка
   ```
   Токен открывает агенту только ручки `/api/agent/*`: прочитать модель и проверки, отправить предложение. Применить или
   отклонить предложение, править модель напрямую и остальное API агент не может. Без `AUTH_USERS` (локальная разработка)
   вход отключён, токен не нужен.
2. Соберите сервер: `npm run build -w server` (MCP-сервер запускается из `server/dist/mcp/index.js`).
3. В Cline откройте MCP Servers → Configure и добавьте сервер по образцу
   [cline_mcp_settings.example.json](cline_mcp_settings.example.json): путь к `index.js`, `PM_API_URL` (адрес приложения)
   и `PM_AGENT_TOKEN` (тот же токен). Для разработки без сборки: `npm run mcp -w server` (tsx).
4. Откройте этот репозиторий в VS Code: правила из `.clinerules/` подскажут Cline, как работать с моделью.

Названия пунктов меню и параметров конфигурации Cline (`autoApprove` и др.) могут отличаться в вашей версии — сверьтесь с
документацией Cline.

## Инструменты MCP-сервера

| Инструмент | Что делает |
|---|---|
| `get_conventions` | Правила Соглашения и формат предложений — читать до первого предложения |
| `list_sessions` | Сессии: id, процесс, код |
| `get_model` | Конспект модели: коды `B002.01.01`, id для ссылок, должности, шаги BPMN, замечания проверок; `scope` — ветка по коду; `view=full` — JSON |
| `propose_patch` | Отправить предложение: список операций. В ответе — описание правок и влияние на проверки (снимает/вносит замечания) либо ошибки |
| `list_proposals`, `get_proposal` | Статус предложений. У отклонённых — **причина отказа**: агент учитывает её в следующих предложениях |

## Формат предложения

`propose_patch` принимает `session_id`, `agent` (роль: методолог, моделист, нормоконтролёр, интервьюер, аналитик), `title`,
`rationale` (почему: цитаты интервью, правило, замечание проверки) и `ops`:

```json
[
  { "op": "add", "collection": "nodes", "value": { "id": "n1", "type": "task", "name": "Открыть реестр", "bpmn_scope": "o1", "role_id": "r2" } },
  { "op": "update", "collection": "nodes", "id": "n1", "patch": { "name": "Открыть реестр процессов" } },
  { "op": "remove", "collection": "flows", "id": "f3" },
  { "op": "set_assignments", "node_id": "o1", "items": [{ "role_id": "r2", "kind": "executor", "functions": ["Внесение данных"] }] },
  { "op": "set_process", "patch": { "code": "B002.00.00" } }
]
```

Коллекции: `roles`, `systems`, `data`, `controls`, `nodes`, `flows`, `pools`, `messages`. Предложение проверяется до сохранения:
ссылки (исполнитель, входы, выходы, системы, родитель, диаграмма) должны существовать, id не повторяются, поток не соединяет
шаги разных диаграмм, запись соответствует схеме модели. При любой ошибке не сохраняется ничего — агент получает список ошибок.
Новые шаги приложение помечает гипотезами, пока аналитик их не подтвердит. Описание формата — `server/src/shared/patch.ts`.

## Что делает аналитик

Вкладка **«Предложения агентов»** внизу студии (и кнопка «Предложения (N)» в ленте):
- видно, что изменится — по-русски, с кодами по Соглашению, — и как изменятся проверки;
- **«Применить»** кладёт правки в черновик студии одним шагом истории: их можно отменить (Ctrl+Z) и сохранить как обычно;
- **«Отклонить…»** записывает причину — агент увидит её через `list_proposals`;
- метка «модель изменилась» — модель сохраняли после предложения; если правки уже нельзя применить к черновику
  (шаг удалён, ссылка пропала), «Применить» недоступно, причина показана.

## Состав агентов и порядок внедрения

1. **Каркас и формат правок** — готово (этот документ).
2. Моделист и Нормоконтролёр с обратной связью друг другу.
3. Методолог (главный агент) и панель «Ассистент».
4. Интервьюер.
5. Аналитик.

Роли описываются в `.clinerules/` (правила и workflows). Будет ли роль запускаться как субагент Cline или главный агент
выполнит её по очереди — зависит от возможностей установленной у вас версии Cline; в обоих случаях все они пользуются одним
MCP-сервером и подписываются в `agent`.
