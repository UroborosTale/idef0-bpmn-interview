# Разработка: стек и как ведётся работа

Документ для человека и агента: что за технологии в проекте, как устроен репозиторий, как здесь принято вносить
правки и что считается «работа сделана». Дополняет `README.md` (описание продукта и ТЗ) и `CLAUDE.md` (память проекта).

## 1. Стек

### Монорепозиторий

- **npm workspaces** в корне: `server`, `web` (плюс `desktop` — не workspace, отдельный .NET-проект).
- Node.js **20+**, TypeScript **5.6**, ESM (`"type": "module"`).
- Всё запускается из корня: `npm run dev:server`, `npm run dev:web`, `npm test`, `npm run typecheck`, `npm run build`.

### Сервер (`server/`)

| Что | Чем |
|---|---|
| HTTP | Express 4, CORS |
| Язык | TypeScript 5.6, ESM, NodeNext |
| Хранилище | SQLite через `better-sqlite3` (каталог `DATA_DIR`, по умолчанию `server/data`) |
| Валидация/контракт модели | `zod` (Process Logic JSON, `server/src/types/model.ts`) |
| Раскладка диаграмм | `elkjs` (BPMN), собственные детерминированные алгоритмы в `server/src/shared/` |
| Экспорт | `jszip` (`.vsdx`), `docx` (Word), `xlsx`, `fast-xml-parser` |
| Импорт документов | `mammoth` (Word), `pdf-parse` (PDF), `xlsx` |
| LLM | `@anthropic-ai/sdk` (Claude), OpenAI-совместимые провайдеры по `LLM_BASE_URL`, офлайн-экстрактор на правилах |
| Агенты/MCP | `@modelcontextprotocol/sdk` — MCP-сервер `process-modeling` |
| Тесты | `vitest` 2.1, `tsx` для скриптов, `playwright` для сценариев, где нужен браузер |
| ID | `nanoid` |

### Клиент (`web/`)

| Что | Чем |
|---|---|
| UI | React 18, React DOM |
| Сборка/дев-сервер | Vite 5, `@vitejs/plugin-react` |
| Общий код с сервером | алиас `@shared` → `server/src/shared` (геометрия, раскладка, коды, валидация) |
| Тесты | `vitest` + `jsdom`, `@testing-library/react`, `@testing-library/user-event`, `@testing-library/dom` |
| Покрытие | `@vitest/coverage-v8` |
| Сквозные тесты | Playwright (`web/e2e`, отдельный `vitest.e2e.config.ts`) |
| Прокси | `/api` → `http://127.0.0.1:8787` |

### Настольная оболочка (`desktop/ProcessStudio/`)

- **.NET 8 WinForms** (`net8.0-windows`, x64) + **WebView2** (`Microsoft.Web.WebView2`).
- Внутри — та же веб-студия, но вместо холста редактора работает **настоящий Visio** через COM.
- Связь студии с оболочкой — `web/src/desktop.ts` (`inDesktopShell`, `postToShell`, `onShellMessage`).
- Сборка: `dotnet build -c Release`; самопроверка `--selftest`; подробности — `docs/desktop-setup.md`.

### Инфраструктура

- `docker-compose.yml` — запуск сервисов в контейнерах (НФТ-6).
- CI `.github/workflows/ci.yml`: Node 20 → `npm ci` → `npm run typecheck` → `npm test` → сборка клиента;
  отдельная задача — `npm run test:e2e` в Chromium.

## 2. Структура репозитория

```
server/                 API-сервер, конвейер, раскладка и выгрузки
server/src/shared/      общий код сервера и клиента (геометрия, коды, валидация, раскладка)
server/src/pipeline/    фрагментация → извлечение → пробелы → валидация → BPMN/IDEF0 → экспорт
server/src/reference/   эталонные модели B002, C025 и демо C090
server/test/            модульные тесты, фаззеры, золотые снимки раскладки
web/                    React-клиент: студия, редакторы BPMN/IDEF0, справочники, отчёты
web/src/components/     компоненты студии и редакторов
web/e2e/                сквозные сценарии в браузере
desktop/ProcessStudio/  настольная оболочка (.NET 8 + WebView2 + Visio)
docs/                   планы, отчёты проверок, ручная приёмка, доступ агентов
.clinerules/            инструкции ролей агентов и правила работы с моделью
```

Ключевое: `server/src/shared/` — единый источник правды для геометрии и раскладки. Правка здесь меняет и серверные
выгрузки, и редакторы в браузере, поэтому после неё обязательны тесты раскладки и золотые снимки.

## 3. Как я работаю

1. **Сначала контекст, потом правки.** Читаю `README.md`, `CLAUDE.md`, `.clinerules/`, `docs/`, затем нахожу точное
   место в коде. Не выдумываю API, имена и поведение: если данных нет — говорю, чего не хватает, или оформляю вопрос.
2. **План перед действием.** Разбиваю задачу на партии (например: раскладка → экспорт → тесты → документ), озвучиваю
   план и только потом правлю.
3. **Правки в стиле проекта.** Те же соглашения об именах и структуре, общий код — в `server/src/shared/`, новые поля
   модели — только необязательные (старые модели читаются без миграции).
4. **Диаграммы — детерминированный код, не LLM.** LLM извлекает факты с цитатами; нотации, раскладку, маршруты и
   валидацию строит наш код.
5. **Сверка с Business Studio 6.** Вид и поведение делаются «1 в 1» с BS6; скриншоты для сверки — `docs/bs6/compare/`.
   Что не совпало — честно перечисляется.
6. **Проверка после каждой партии.** `npm run typecheck` → `npm test` → при клиентских правках `npm run test:e2e`.
   Для больших серверных прогонов удобно запускать vitest через `Start-Process` с выводом в файл (см. правила окружения).
7. **Золотые снимки — осознанно.** Изменились `__golden__` — смотрю diff и обновляю только с обоснованием
   (`npx vitest run <файл> -u`). Обновление «чтобы тесты прошли» без просмотра diff недопустимо.
8. **Документирую результат.** Что сделано и что проверено — в `docs/fixes-*.md`; счётчики тестов — в
   `docs/test-report-*.md`; что нужно посмотреть глазами — в `docs/manual-checks.md`.
9. **Коммит — одна осмысленная партия.** Сообщение в формате `fix: краткая суть (номера пунктов)`. В ответе аналитику:
   что сделано, номер коммита, что проверено тестами, а что вживую не проверено.
10. **Честность важнее «зелёного отчёта».** Если пункт не закрыт или закрыт частично (компромисс), это пишется прямо,
    с причиной и числами. «Проверено глазами» не выдаётся за проверенное тестами и наоборот.

## 4. Тесты и проверки

| Уровень | Где | Что проверяет |
|---|---|---|
| Модульные | `server/test/**/*.test.ts` | ядро: IDEF0, BPMN, валидация, VSDX, конвейер, вход, хранилище, история |
| Компонентные | `web/src/**/*.test.ts(x)` (jsdom + Testing Library) | операции над моделью, геометрия, маршрутизация, транспорт, панель свойств, навигатор, проверки, студия |
| Золотые снимки раскладки | `server/test/layoutGolden.test.ts`, `web/.../layoutGolden.test.ts`, `__golden__` | координаты блоков, стрелок, подписей, значков и пулов на эталонах B002, C025, демо |
| Фаззинг | `server/test/*.fuzz.ts`, `vitest.fuzz.config.ts` | ручки API случайными телами, странные модели во всех выгрузках; ожидается ноль находок |
| Сквозные | `web/e2e/*.e2e.test.ts` (Playwright) | реальный браузер: свой API на временной базе (порт 18787), свой Vite (15173), сценарии студии |
| CI | `.github/workflows/ci.yml` | typecheck, тесты сервера и клиента, сборка клиента, e2e в Chromium |

Особенности e2e: на Windows используется установленный Edge, иначе Chromium Playwright; `E2E_BROWSER_CHANNEL` и
`E2E_HEADED=1` — переключатели; временная база и офлайн-экстрактор, чтобы не тратить токены LLM.

## 5. Команды

```bash
npm install                # зависимости server + web (workspaces)
npm run dev:server         # API, http://127.0.0.1:8787
npm run dev:web            # клиент, http://localhost:5173 (проксирует /api)
npm run typecheck          # типы сервера и клиента
npm test                   # vitest: сервер + клиент
npm run test:e2e           # сквозные тесты (Edge на Windows)
npm run build              # сборка сервера и клиента
npm run fuzz -w server     # фаззинг API и выгрузок
npm run backup -w server   # копия базы (-- --repo — ещё и репозиторий одним bundle)
npm run restore -w server -- <файл.sqlite> --yes
npm run seed:b002 -w server            # эталон B002 новой сессией
npm run seed:c025 -w server            # процесс C025 новой сессией
npm run seed:demo -w server            # демо-процесс C090
npm run reset:process -w server -- b002 --replace <id сессии>   # заменить модель сессии эталоном
npm run hash-password -w server -- <пароль>                     # хэш для AUTH_USERS
npm run mcp -w server                  # MCP-сервер process-modeling
```

## 6. Жёсткие соглашения проекта

- **Веб и настольная версии живут вместе.** Одна модель, одна база; правки не должны ломать ни одну из них.
- **Совместимость модели.** Новые поля — только необязательные; старые модели читаются без миграции.
- **Чужое не копируем.** Берём идеи и форматы, но не код, ресурсы и файлы Business Studio и Microsoft (EULA).
- **Жесты:** двойной щелчок — правка текста, **Ctrl + двойной щелчок** — создание функции IDEF0 и излома стрелки.
- **Модель — через приложение.** Модель управляется приложением (MCP-сервер `process-modeling`), прямые правки JSON
  или базы не делаются: агент отправляет `propose_patch`, применяет аналитик.
- **Конфиденциальные сессии** закрыты для агентов; разрешение даётся в студии, обходить запрет нельзя.
- **Секреты.** `.env` и история чатов не в git; ключи не выводить в чат, отчёты и коммиты.

## 7. Окружение этой машины

- Windows, PowerShell. Сетевые запросы идут через прокси: `curl.exe` прокси уважает, `Invoke-WebRequest` в
  PowerShell 5.1 — нет.
- PowerShell 5.1 читает `.ps1` как ANSI: скрипты писать только ASCII, пути с кириллицей передавать параметром.
- .NET 8 установлен для пользователя (`%LOCALAPPDATA%\Microsoft\dotnet` + `DOTNET_ROOT`); сборка
  `desktop/ProcessStudio` — `dotnet build -c Release`.
- Долгие прогоны vitest удобно запускать в фоне с перенаправлением вывода в файл и читать хвост; так не блокируется
  терминал и видно итоговые счётчики.
- Вход по умолчанию отключён (нет `AUTH_USERS`), сервер слушает `127.0.0.1`.

## 8. Что остаётся после работы

- `docs/fixes-*.md` — что исправлено по итогам проверки, с номерами пунктов и статусом.
- `docs/test-report-*.md` — счётчики тестов и результаты прогонов.
- `docs/manual-checks.md` — что нужно проверить глазами.
- `__golden__` — эталонные координаты раскладки; изменения только с просмотром diff.
- Сообщение коммита и ответ аналитику — краткий отчёт: сделано / проверено тестами / не проверено вживую.

## 9. Границы для агента

- Инструкции ролей лежат в `.clinerules/workflows/` (методолог, моделист, нормоконтролёр, интервьюер, аналитик);
  агент работает по инструкции своей роли и не выходит за её границы.
- Предложения по модели отправляются через `propose_patch` с обоснованием (`rationale`) и цитатой из `get_fragments`;
  чего нет в тексте и модели — оформляется как вопрос аналитику.
- При ответе «слишком много» (429) работа с предложениями останавливается, о ситуации сообщается аналитику.
